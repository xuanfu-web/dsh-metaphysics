# 性能与稳定性优化方案（v0.14.3 基线）

> 结论先行：**计算逻辑本身已经很快（热路径 bazi 0.57ms、全体系 1000 盘 233ms），
> 真正的瓶颈不在算力而在「重复计算」与「前端包体积」；稳定性风险不在异常崩溃，
> 而在「同一规则有多份实现」与「引擎导出的函数不做入参守卫」。**
> 本次已落地两项（节气按需计算、旬空单一真源），bazi 单盘 -41%，
> 其余按 P0/P1/P2 排期，每项都给了可执行的步骤与验证方式。

| 指标 | 基线值 | 采集方式 |

### 1.3 已确认的四个结构性问题

1. **冷启动成本集中在节气求解**，且「算得比用得多」：`termWindow(year)` 一次算 3 年 × 24 = 72 个节气，
   而八字只用「节」定月柱，十二「气」纯属白算。
2. **同一规则多份实现**：旬空在 `bazi.js`（`(start+10)%12`）、`liuyao.js`（`(10-2k)%12`）、
   `daliuren.js`（查表）各一份，公式形式互不相同，改一处极易漏改另两处。
3. **引擎导出函数不做入参守卫**：实测 `buildBazi({ datetime: '1970-06-15T03:20' })` 直接抛
   `TypeError: Cannot read properties of null (reading 'index')`，而不是 `E_INPUT`。
   工具层（`index.js`）有兜底，但任何直接调用引擎的地方（测试、面板、二次开发）都会踩。
4. **前端包未压缩**：`tools/build-client.mjs` 只做模块拼接与去缩进，无 minify；`dsh.client.immediately: true`
   意味着面板一打开就加载这 423KB。

## 二、优化目标与优先级

排序原则：**先消除「错得无声」的风险，再省「用户能感知」的时间，最后治「改起来痛」的结构**。

| 优先级 | 目标 | 判据 | 状态 |
|---|---|---|---|
| P0 | 同类规则只能有一份实现 | 任一规则改动只改 1 处；有全量对拍测试 | 旬空 ✅ / 纳甲、纳音、三合 ⬜ |
| P0 | 引擎边界失败必须给错误码 | 错误输入 100% 返回 `E_*`，无裸 TypeError | ✅ `engine/validate.js` + `test/contract.test.mjs`（15 类坏输入） |
| P1 | 冷启动 ≤ 基线 60% | bazi 首次 < 1.8ms、termWindow 新年度 < 1.2ms | ✅（实测 1.6ms / 1.0ms） |
| P1 | 前端包体积 ≤ 100KB gzip | gzip 后 clien.js | ⬜（当前 136KB） |
| P2 | 热路径不回退 | bazi p50 < 1.5ms、1000 盘 < 400ms | ✅（0.57ms / 233ms） |
| P2 | 可观测 | 一条环境变量输出分段耗时与缓存命中率 | ✅ `DSH_METRICS=1` 打印各项缓存命中率 |

## 三、已实施（分支 `perf/0.15-opt`，commit c3678ae）

### 3.1 节气按需计算 + 三年窗口共享缓存（计算逻辑）

- `termWindow(year, { jieOnly: true })`：八字只取十二「节」，求值量减半；
  若该年全年窗口已在缓存（紫微/奇门先算过），只取节时**直接过滤复用**，避免两边各建一份。
- `termYearList` 按 `(年, 是否只取节)` 双键缓存，相邻年份窗口（year±1）不再重复计算。
- 牛顿迭代容差 `1e-7° → 1e-5°`：实测迭代 131 → 105 次，节气时刻最大差 **0.02 秒**（输出只到分钟）。
- 相邻年份以上一年同节气 + 回归年（365.2422 日）作初值，第二年起成本再降约 45%。

### 3.2 旬空收敛为单一真源（可维护性）

- 新增 `calendar.xunKongOf(ganzhi)`，返回两个空亡地支；非干支入参返回 `[]` 而不抛异常。
- `bazi.js` / `liuyao.js` / `daliuren.js` 三处实现全部改为调用它，删除各自公式与查表。
- 新增 `test/xunkong-parity.test.mjs`：六十甲子全量对拍 + bazi 四柱回归 + liuyao 六十日旬空/旬首回归。

### 3.3 实测效果（同机 A/B，各 3 轮取中位数；基线用 `git worktree` 拉 main）

| 指标 | 基线 | 优化后 | 变化 |
|---|---|---|---|
| bazi 单盘（`compute` 全流程，含首次建窗口） | 2.70ms | 1.60ms | **-41%** |
| ziwei 单盘 | 1.35ms | 1.12ms | -17% |
| qimen 单盘（隔离测，无前置缓存） | 2.30ms | 1.78ms | -23% |
| `termWindow` 全新年份 | 1.50ms | 1.00ms | -33% |
| `termWindow` 相邻年份 | 0.52ms | 0.35ms | -33% |
| 全套测试 | 44 文件 / 1147 断言 | 45 文件 / 1152 断言 | 全绿，CI 五闸通过 |

> 口径提醒：多体系混合负载下（先 bazi 后 qimen 同一年），总计算量不变，只是把成本从八字侧挪到奇门侧；
> 单盘请求（最常见的用法）是净收益。基准脚本 `node tools/bench.mjs` 可复现。

## 四、待实施项：具体步骤与验证

### P0-1 引擎边界入参守卫

**问题**：`buildBazi` / `buildZiwei` / `buildLiuyao` 等导出函数假设调用方已解析好 `{year, month, day}`，
传错形状时以 `TypeError` 崩溃（已实测复现）。

**步骤**
1. `engine/validate.js` 增加 `assertCivil(input, who)`：检查 `year/month/day` 为整数、范围 1600–2400、
   `hour 0-23 / minute 0-59`，失败抛 `fail('E_INPUT', ...)`；`gender` 复用 `index.js` 的 `requireGender`。
2. 各 `build*` 首行调用它；`datetime` 字符串**不**在此接受（保持「解析归 Host 层」的职责划分）。
3. 新增 `test/contract.test.mjs`：表驱动 12 组坏输入 → 断言错误码恒为 `E_INPUT`、文案含修复提示。

**验证**：新测试全绿；`tools/verify-tests-can-fail.mjs` 确认断言有效；面板不受影响（面板走 `compute`）。

### P0-2 缓存层统一

**问题**：四处缓存各自为政——`TERM_INSTANT_CACHE`（4096，FIFO）、`TERM_YEAR_CACHE`（32）、
`TERM_WINDOW_CACHE`（8）、`geoCache`（200，带 TTL）；淘汰策略与上限不统一，无从观测命中率。

**步骤**
1. `engine/lru.js` 提供 `createLru({ max, ttlMs })`，带 `hits/misses/evictions` 计数。
2. 四处改为该工厂创建，保留各自上限值（行为等价，先统一结构再调参）。
3. `DSH_METRICS=1` 时在 `renderText` 后打印各缓存命中率。

**验证**：对拍——同一批 200 个年份排盘，改前改后输出逐字节相同；命中率表落在基准脚本输出里。

**已实现**：`engine/lru.js` + 四处接入（`termInstant` 4096 / `termYear` 32 / `termWindow` 8 / `geo` 200+TTL），
`DSH_METRICS=1` 时 `renderText` 往 stderr 打一行
`termInstant: 命中 289/385（75.1%），缓存 96/4096，淘汰 0`；`test/lru.test.mjs` 钉住淘汰顺序、TTL 与命中率。

### P1-1 前端包压缩

**步骤**
1. `tools/build-client.mjs` 末尾增加压缩步骤：优先 `esbuild`（`--minify --target=es2020`，
   保留 `window.__ModuleLoader__.load({id, factory(require){...}})` 包装不动）；未装 esbuild 时退回 `terser`。
2. `test/client-bundle.test.mjs` 增加体积断言：gzip < 100KB、factory 可被 `new Function` 正常解析。
3. 压缩产物必须通过 `test/standalone.test.mjs` 与 `test/interact.test.mjs`（真实渲染路径）。

**验证**：`npm run build && npm test` 全绿；面板首屏加载时间用 DevTools 记录，对比 423KB→~150KB 的传输差异。

### P1-2 `jsonSafe` 去 JSON 往返

**问题**：`engine/index.js:273` 每次 `compute` 都 `JSON.parse(JSON.stringify(value))`，
紫微带解析时对象可达 100KB+，纯为去掉 `undefined`。

**步骤**
1. 改为 `structuredClone`（Node 18+ 自带），再对结果做一次浅层 `undefined` 清理；
2. 或直接在各 `build*` 返回处保证不产生 `undefined`（更好，但改动面大）——先做 1，作为过渡。

**验证**：`test/golden.test.mjs` / `baseline.test.mjs` 输出对拍不变；基准脚本看 bazi+interpret 的 p50。

### P2-1 数据表集中

纳音（`bazi.js`）、纳甲（`liuyao.js`）、三合/方局（`shensha.js`）、旬空（已统一）分散在各引擎。
建议建 `engine/tables/`，并在 `tools/check-patterns.mjs` 里加一条约定：引擎文件不得直接定义超过 20 行的干支表。

### P2-2 分段耗时观测

`DSH_METRICS=1` 时输出 `parse / calendar / engine / interpret` 四段耗时与缓存命中率，
便于把「用户说慢」定位到具体段，而不必每次都跑基准脚本。

## 五、验证体系（每项改动的固定动作）

1. **先加对拍，再改实现**：改任何规则前，先写「旧实现 vs 新实现」全量对拍测试（如旬空的六十甲子）。
2. **四道现有闸门必过**：`test-all` → `check-assertions`（断言数不得下降）→
   `verify-tests-can-fail`（测试必须能失败）→ `check-html-sinks` / `check-patterns`。
3. **同机 A/B 基准**：`git worktree add baseline main` 起基线，`node tools/bench.mjs` 各跑 3 轮取中位数，
   不接受「体感变快」。
4. **真实典籍对拍**：《卜筮正宗》138 条卦例（拆卦例数据集）作为外部验证集，
   校验卦名讹字、动爻数、缺爻伏神、纳甲六亲，通过后进 `test/fixtures/`。
5. **回滚策略**：每项改动单独 commit；`perf/0.15-opt` 分支验证通过前不合 main，可整支丢弃。
