## 2. 关键决策与理由

### 2.1 本地部署：为什么选 Ollama 而不是 llama.cpp / LM Studio

- **决策**：Ollama 0.40.10 + qwen3:4b（Q4 量化，2.5GB）。
- **理由**：机器是 RTX 4060 Ti 8GB + 64GB 内存。Ollama 自带 CUDA 加速、OpenAI 兼容 API、模型管理，零配置；llama.cpp 要自己编 CUDA 版本，LM Studio 体积更大且闭源。
- **代价**：安装包 1.6GB（含 CUDA 库）；服务需常驻。
- **实测**：显存占用 4.4GB、生成 81.5 token/秒，中文输出正常。

### 2.2 Chatbox 而不是 Open WebUI

- **决策**：Chatbox 1.23.5 桌面端。
- **理由**：Open WebUI 需要 Docker 或 Python 服务常驻，对非开发用户太重；Chatbox 是纯桌面应用，填一个地址就能用。
- **踩坑**：Chatbox 在自动化环境（PowerShell Start-Process、`stdio: ignore`）启动会**秒退且无日志**，必须经 explorer 启动（等价双击）。这不是模型问题，是它自身的限制。

### 2.3 Gmail：为什么不用现成连接器

- **决策**：自建本地 Gmail MCP 服务器（`reisbel/gmail-mcp`），而非等官方连接器。
- **理由**：连接器市场里只有 QQ 邮箱、企业微信等，没有 Gmail。本地 MCP 用用户自己的 Google OAuth，邮件数据不经第三方，符合「本地优先」的一贯主张。
- **代价**：需要用户自己去 Google Cloud 建 OAuth 桌面应用凭据（约 10 分钟，无法代做）。
- **风险**：测试模式 refresh token 连续 7 天不用会过期，需重跑授权。

### 2.4 拆卦例：为什么以 PDF 页码为唯一出处

- **决策**：每条卦例记 PDF 页码 + 书页 + 章节；判定分 pass / warn / reject 三级。
- **理由**：源文件是**扫描图像版、无文字层**，任何 OCR 结果都必须能回到原图复核。页码是最硬的锚点。
- **代价**：必须逐页看图，无法批量自动化（138 条约需 30 页人工核对）。
- **已得结论**：p78–p113 共 36 页、每页 2×2 四条；首批 9 条中 8 条十项全过，说明表格本身可靠，剔除率会低于预期。

### 2.5 性能优化：为什么是「少算」而不是「加缓存」

- **决策**：八字只用十二「节」（`jieOnly`），不连带计算用不上的「气」；相邻年份用回归年作牛顿初值。
- **理由**：实测冷启动 7.4ms 里几乎全在节气求解（一次算 3 年 × 24 个）。加缓存只能优化第二次；**少算**才能优化第一次。而 chat 场景每个盘往往只算一次。
- **代价**：多体系混用时（先八字后奇门、同一年），总计算量不变，只是成本从八字侧挪到奇门侧。单盘请求是净收益。
- **实测**：bazi 单盘 2.70ms → 1.60ms（-41%），termWindow 新年度 1.50ms → 1.00ms（-33%）。

### 2.6 旬空：为什么必须收敛成一份

- **决策**：新增 `calendar.xunKongOf`，bazi / liuyao / daliuren 三处全部改为调用它。
- **理由**：原先是三份实现，公式形式互不相同（`(start+10)%12`、`(10-2k)%12`、查表）。三者当前结果一致，但只要有人改其中一处，就会静默漂移——这类 bug 不会报错，只会让某一年份的盘悄悄算错。
- **代价**：动三个引擎，风险靠新加的六十甲子全量对拍测试兜住。

### 2.7 口径差异：为什么把它做成产品特性

- **决策**：`engine/diff.js` 区分「根因字段」（柱干支/日辰/局数/爻）与「连带变化」（神煞/大运/流年/格局），一句话总结因果。
- **理由**：命理圈争得最凶的就是口径（晚子时、真太阳时、拆补 vs 置闰、闰月归月），但所有工具切换后只给新结果。**谁会主动暴露自己的口径分歧，谁才赢得专业信任。**
- **实测效果**：23:40 出生切晚子时 → 根因仅 2 处（日柱丙辰→乙卯、时柱戊子→丙子），连带 406 处。

### 2.8 文案：为什么是「加一层」而不是「重写」

- **决策**：保留原有五维度（专业表述、依据、建议），在其上叠加「直答 / 说人话 / 每维一句话 / 追问」四层。
- **理由**：原文案的专业度是资产，重写会丢；缺的是入口。四层解决「从哪读起、读完怎么问」。
- **关键细节**：术语表**必须按体系区分**——「用神」在八字是喜用五行、在六爻是所问之事的代表爻、在紫微是用神宫。共用一条解释会直接误导。
- **边界**：每维一句话目前只有八字有（其余体系取不到足够盘面数据），**没有硬凑**。

### 2.9 知识库：为什么每条都要标「有多稳」

- **决策**：28 条规则，三级状态：诸家一致 13 / 各家有异说 13 / 待核实 2；variant 与 todo 强制写 note。
- **理由**：命理最容易犯的错不是算错，而是「说得很确定、却没人知道依据在哪」。标出分歧与缺口，是把「可验证」落到文案层。
- **代价**：文案变长、有时显得啰嗦；且需要维护 note（改一处要同步说明）。
- **反常识点（特意写进去）**：神煞是标签不是判决；旺相休囚死是相对排序不是吉凶等级；岁运并临只作变动提示；六神不是主角。

### 2.10 发布：为什么每次都单独确认

- **决策**：每次内容变更后，先给本地预览，再单独问「是否同步线上」。
- **理由**：线上链接可能已经被别人打开，覆盖是不可逆的。同意发布一次不等于授权下一次。

## 4. 口径与约定（接手必读）

1. **判定分级**（拆卦例）：pass 全过 / warn 仅原文缺录 / reject 硬矛盾（卦名与卦象不符、动爻数不符、纳甲错、六亲错、卦宫五行错、伏神位置错）。
2. **知识库状态**：settled 诸家一致 / variant 各家有异说（必写 note）/ todo 待核实（必写 note）。
3. **文案禁用词**：一定、必然、注定、肯定会、绝对会、百分百、铁定、毫无疑问（测试会拦）。
4. **错误码优先**：入参错误抛 `E_INPUT` / `E_RANGE` / `E_SYSTEM` / `E_LINES` / `E_ASOF`，不在引擎里裸抛 `TypeError`。
5. **发布流程**：本地构建 → 预览 → 单独确认 → 部署 → 抓取线上页面验证（不是「部署返回成功」就当成功）。
